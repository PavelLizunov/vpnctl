# Восстановление доступа к фильтруемому VPN-узлу

Узел с работающими службами и недоступным прямым IP можно сохранить в работе.
Перезапуск службы не исправляет потерю SYN до интерфейса VPS. Cheburcheck
помогает увидеть региональную фильтрацию; его вердикт не меняет маршруты сам.

## Практический порядок

1. **Сохранить управление.** Доступный pinned SSH relay через Нидерланды
   позволяет администрировать исходный VPS. `jump_via` относится только к SSH.
2. **Вернуть совместимый клиентский вход.** Существующий `client_detour_via`
   задаёт цепочку клиент → доступный NL entry → исходный exit. Она сохраняет
   конечную страну/IP выхода, но меняет клиентский артефакт.
3. **Отделить неподдерживаемые клиенты.** Sing-box и Mihomo поддерживают цепочки;
   VPNRouter — VLESS Reality с `detour-v1`. URI-only клиенты chained target не
   получают. Отдельные WireGuard/AmneziaWG `.conf` при такой политике не выдаются;
   универсальное массовое переключение всех форматов этим не достигается.
4. **Вернуть прямой путь, если он необходим.** Выяснить у хостера возможность
   нового адреса, желательно другого префикса, либо переноса на другую сеть.
   Новый адрес из того же фильтруемого диапазона может не помочь. Цена,
   доступность замены и долговечность нового маршрута заранее неизвестны.

Выход через NL как обычный VPN-узел проще двух хопов, но меняет конечную
страну/IP. Вход через NL с выходом через старый VPS сохраняет его назначение,
потребляя дополнительный канал и соединения на NL. Низкая CPU load не доказывает
запас полосы. Реальный критерий цепочки — передача данных с ожидаемым конечным
exit IP, отдельно для нужного TCP/UDP транспорта.

## Другие варианты и границы

- **L4 relay** на доступном входе может передавать исходный TCP/UDP протокол.
  Нужен свободный публичный IP/порт, поддержка требуемого UDP и учёт MTU.
  Обычный HTTP reverse proxy не заменяет L4 passthrough. Если TCP443 уже занят
  действующим VPN-входом, занятие того же адреса/порта другим relay нарушит его.
- **IPv6** может дать отдельный маршрут, если он есть у сервера и клиента и не
  фильтруется. Это требует отдельного наблюдения, а не предположения по IPv4.
- **Hostname** полезен для последующей смены адреса только при корректном DNS.
  Он не переносит пакеты мимо блокировки IP сам по себе. DNS, SSH identity и
  фактический VPN transfer — разные свойства; открытого TCP-порта недостаточно.
- **Reality SNI или другой протокол на том же IP** не являются доказанным
  исправлением IP-level drop. Исследовать протокол имеет смысл, когда пакеты
  действительно доходят до сервера, а разрыв относится к handshake/data phase.
- **Старый буквальный IP в статическом профиле** не обновится серверным redirect,
  если пакеты уже не достигают старого адреса. Нужны новый импорт, обновляемая
  подписка либо заранее настроенный доступный запасной вход.

## Как уменьшить обрывы автоматически

Для следующей доработки нужен заранее доступный NL entry и обновляемая
подписка либо клиент с уже импортированным резервом. Переключение на стороне
контроллера не поможет клиенту, который знает только недоступный буквальный IP.
Cheburcheck может объяснить региональную проблему, но не должен единолично
включать failover: `uncertain`, 429 и отказ самого сервиса не доказывают отказ VPS.

Решение о переключении должно опираться на несколько последовательных ошибок
реального VPN transfer из нужной клиентской сети и успешный transfer через
резерв. Приоритет входа — Нидерланды; Швеция — запасной вариант с учётом
пропускной способности. Переключение следует ограничить совместимыми форматами
и grants, записывать прежний/новый путь и причину в audit, а возврат выполнять
после устойчивого восстановления с паузой между сменами, чтобы избежать
колебаний. Ошибка единственного внешнего наблюдателя не должна менять всех
пользователей. Это проект следующей доработки, не включённая автоматика.

## Текущие возможности панели

В Server → Setup доступны отдельные поля управления SSH и клиентского входа.
Перед выдачей цепочки проверяются роли и grants обоих узлов, поддерживаемый
формат и совместимый entry transport. Наблюдение через relay не подменяет
прямую клиентскую доступность.

Текущая интеграция Cheburcheck показывает списки, региональные результаты и
неопределённость, но не включает автоматически `client_detour_via`, смену IP,
покупку VPS или массовое обновление артефактов. Эти действия зависят от фактических
клиентов и выбранного способа восстановления. Документ описывает варианты;
новый IP, IPv6 и end-to-end клиентские цепочки этой интеграцией не проверялись.

Контракт: [client-detour](../specs/client-detour.md). Первичная документация:
[sing-box detour](https://sing-box.sagernet.org/configuration/shared/dial/#detour),
[Mihomo dialer-proxy](https://wiki.metacubex.one/en/config/proxies/dialer-proxy/),
[TCP/UDP relay](https://nginx.org/en/docs/stream/ngx_stream_proxy_module.html).
