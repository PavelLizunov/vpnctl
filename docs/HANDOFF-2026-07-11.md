# 2. Gotchas & conventions

## Gotchas discovered this session

### (a) 192.168.0.236 cannot reach db-ip.com's Cloudflare CDN — proxy such fetches through a node

The homelab control host **cannot complete downloads from db-ip.com's Cloudflare
CDN**. The transfer stalls after ~12–20 KB regardless of MSS clamping, while large
**non**-Cloudflare downloads run at 20+ MB/s and a `HEAD` to db-ip returns 200. It
is a Cloudflare-vs-homelab-WAN-IP block, **not** an MTU/MSS problem and **not**
fixable on 236 or in vpnctl. Symptom when it bites: `vpnctl geoip-update` fails
with `Connection timed out (os error 110)` and the GeoIP DBs freeze (they were
stuck at `2026-05` until TT-6).

**The fix pattern — reuse it for any other stalling fetch from 236.** The VPN nodes
reach db-ip fine (~23 MB/s), and vpnctld already SSHes to them with the deploy key,
so stream the download *through a node*:

```bash
ssh -i /var/lib/vpnctl/.ssh/id_ed25519 <node> "curl -fsSL <url>" > out.partial
```

`scripts/vpnctl-geoip-fetch-via-node.sh` is the canonical template: it iterates the
non-ProxyJump nodes from `inv.db` (`file:...?immutable=1` so it works even with
vpnctld down / a WAL DB in a read-only dir), fetches current-then-previous month,
**validates before swapping** (gunzip OK + `MaxMind.com` marker in the tail +
size > 1 MB), and only then atomic-renames into `VPNCTLD_GEOIP_DIR` — a failed run
never clobbers good data. It runs under the `vpnctl-geoip-update.service` strict
sandbox (`User=user`, `ProtectHome`, `ProtectSystem=strict`), which is why the unit
needed `HOME=/var/lib/vpnctl` added alongside the `ExecStart` repoint. The refreshed
mmdb is loaded by `daemon/src/geoip.rs` (`GeoLookup`) mmap-at-startup, so no restart
is forced — the next deploy picks it up.

### (b) The .210 front proxy MUST be in `VPNCTLD_TRUSTED_PROXIES` or client IPs collapse to the proxy IP

Live request chain into prod: `client → router 192.168.0.1 (DNAT) → Caddy
192.168.0.210 ("ingress", LAN-only, own ACME) → vpnctld 192.168.0.236`. 236's
`VPNCTLD_TRUSTED_PROXIES` listed only `192.168.0.207`, so `resolve_real_ip`
(`daemon/src/real_ip.rs`) refused to trust `.210`'s `X-Forwarded-For` and logged
the **proxy's** private IP into `sub_access_log.ip`. Every client behind that hop
collapses into one IP → geolocation, /16-clustering and all IP-based abuse
intelligence break. This is the same class of failure already documented in
CLAUDE.md's «Грабли» for the 2026-05-23 `.207` incident — the trusted-proxies
list is **per-front-proxy** and must be updated whenever a new terminating proxy
is added.

The live fix (TT-0, infra only, **not in git**):
- **236:** `VPNCTLD_TRUSTED_PROXIES="192.168.0.207,192.168.0.210"` + restart
  vpnctld (backup at `/etc/vpnctl/vpnctld.env.bak-tt0-*`).
- **.210 Caddy:** on the **two** `192.168.0.236`-targeting `reverse_proxy` blocks
  in `ninitux.com.caddy` (`@valid` + `@junk`, **not** the `.207` landing) add
  `header_up X-Real-IP {http.request.remote.host}` +
  `header_up X-Forwarded-For {http.request.remote.host}` (backup
  `/etc/caddy/conf.d/ninitux.com.caddy.bak-tt0-*`). `X-Real-IP` feeds the
  spoof-proof `resolve_peer_real_ip` used for the security/rate-limit key; the
  `X-Forwarded-For` set makes the *logged* IP unspoofable.

E2E-verified: a fetch through the public endpoint now logs the real client IP
(`194.87.222.111`) instead of `192.168.0.210`.

### (c) The git-gate pre-commit/push hook fails "cargo not found" in worktrees

The blocking git hook shells out to `cargo` on commit/push. In a
`git worktree`-checked-out tree the hook runs in an environment where `cargo`
isn't on `PATH`, so it aborts with "cargo not found" before your real gate has a
chance to run. **Sanctioned workaround: run the gate manually** (review-agent +
`cargo fmt --all --check` + `clippy -D warnings` + `test --workspace`, per the
CLAUDE.md workflow rules) **then commit with `--no-verify`.** This matches the
already-recorded MEMORY note ("git-gate hook tests the wrong tree → manual gate +
`--no-verify`"). Do not treat `--no-verify` here as skipping the gate — you still
owe the full local CI; you are only bypassing a hook that can't see your toolchain.

### (d) 6 `admin_smoke` `*_auto_deploy` tests fail on Windows-LOCAL but are green on Linux CI

Six `admin_smoke` tests whose names end `_auto_deploy` fail when run locally on
Windows because they exercise the subprocess-`ssh` deploy path
(`SubprocessSshTransport`), which behaves differently under the Windows shell than
under Linux CI where they are green. **Before assuming a red `*_auto_deploy` is
your regression, confirm "is it mine?" by running the same test on a pristine
`origin/main` checkout first** — if it's red there too, it's the platform, not your
diff. The authority for pass/fail is Linux CI, not the Windows working tree.

## How to continue / conventions

### Multi-session discipline (BLOCKING — shared tree, several concurrent sessions)

Pavel drives **several parallel Claude sessions in the same working tree**. Per
CLAUDE.md's multi-session rules:

1. **`git branch --show-current` before every commit.** Another session may have
   switched the tree at any moment — never assume `main`, even if it was `main`
   when your session started.
2. **Stage only your own files.** Never `git add -A` / `git add .` — the tree
   almost always holds another session's uncommitted edits. `git status --short`
   first; don't stage or "fix" someone else's `M`/`??` files.
3. **Don't touch other sessions' state.** No `reset --hard` / `checkout` / `stash`
   / `clean` reaching files or branches you don't own. If your commit landed on a
   foreign branch: `git worktree add` from main → `cherry-pick <sha>` → on the
   other branch `git reset --keep <sha>~1` (`--keep`, **not** `--hard`).
4. **Work destined for main goes through your own worktree**
   (`git worktree add /tmp/vpnctl-<topic> main`), not by switching the shared tree.
   A worktree build needs its **own** `target/` — pointing `CARGO_TARGET_DIR` at
   the shared target fails with "cannot find binary path".
5. **Deploy to 192.168.0.236 ONLY from `main` with CI green.** There is one prod
   daemon; deploying from a feature branch overwrites the binary and loses other
   sessions' fixes. Back up the current binary first
   (`sudo cp -a /opt/vpnctl/vpnctld /opt/vpnctl/vpnctld.bak-<label>`).
6. **After `git pull`, re-check the branch** — a pull on a foreign branch drags
   *its* upstream, not main; "Merge … into `<branch>`" in the pull output is a red
   flag that you're not on main.

### Review-before-commit methodology (BLOCKING)

For every feature/refactor/fix, in order (CLAUDE.md "Workflow rules"):

1. **Review-agent** — an independent `general-purpose` subagent that sees **only
   the diff** (brief it like a new colleague — paste the full diff + the
   architectural invariants; never "as we discussed"). Returns a JSON findings
   list; address `critical`/`important`, `minor` is opt-in. Use the review-agent
   prompt template verbatim from CLAUDE.md.
2. **Test-writer-agent** — for any new public function/API, a `general-purpose`
   subagent that gets **only the spec** (signatures + behaviour contract, no
   implementation) and writes `tests/spec_*.rs`. A test that fails is either a
   real bug or an ambiguous spec — never weaken the test to make it pass.
3. **Local CI gate — `just ci`** (fmt-check + `clippy -D warnings` + test + deny).
   No green, no commit. **Run `cargo fmt --all` (not just `--check`) before the
   tests** — fmt is the single most frequent CI-killer here; test-writer output,
   mass Python/sed edits, and any ≥2-file commit all tend to drift.

The review-agent may be skipped **only** for a true hotfix meeting all three
conditions simultaneously: impl ≤ 5 lines, touches exactly one surface, and
changes no output pinned by a `*_byte_equal*` test. Pure docs/README/CLAUDE.md
edits skip steps 1–2 but still owe `just ci`.

**After push:** `gh run watch <id> --exit-status` — block until CI finishes. Red →
`gh run view --log-failed` → fix → re-push. **Do not commit new code atop unresolved
red CI.**

### Deploy recipe (control plane, 192.168.0.236)

The build host is 236 itself (native `cargo`, warm cache); source is built from
`origin/main` after CI is green. The tar-pipe pattern (mirrors the prior handoff's
runbook, avoids depending on a checkout already on 236 being current):

```bash
# From your dev machine, ship main's tree to the build host:
git archive origin/main | ssh user@192.168.0.236 \
  'rm -rf ~/vpnctl-build && mkdir ~/vpnctl-build && tar -x -C ~/vpnctl-build'

# On 236 — native build + install with a rollback backup + restart:
ssh user@192.168.0.236 '
  source ~/.cargo/env &&
  cd ~/vpnctl-build &&
  cargo build --release -p vpnctld &&
  sudo cp -a /opt/vpnctl/vpnctld /opt/vpnctl/vpnctld.bak-$(date -u +%Y%m%d-%H%M%S) &&
  sudo install -m0755 target/release/vpnctld /opt/vpnctl/vpnctld &&
  sudo systemctl reset-failed vpnctld && sudo systemctl restart vpnctld'
```

Building natively **on** 236 (glibc matches the host) sidesteps the cross-glibc
hazard that made the container path need `cargo zigbuild --target
x86_64-unknown-linux-gnu.2.36`. A daemon restart is a brief admin-UI blip with
**no VPN impact** — node sing-box configs are untouched. Deploying **node** configs
is a separate action (admin UI "Deploy all" / per-server), which restarts sing-box
and drops that node's connections; stage those deliberately.

For any change under `crates/protocols/`, `crates/kernels/`, or
`daemon/src/handlers/`, the redeploy is **mandatory** — local tests and CI pass
green while the live `/sub` and `/api/v1/app/config` endpoints keep serving the
**old** bytes until the binary on 236 is rebuilt and restarted. Verify the changed
code path with a curl afterward.

No `unwrap`/`expect`/`panic!` outside `#[cfg(test)]`; no `unsafe`; Kernel × Protocol
orthogonality (a new kernel/protocol touches only `crates/kernels|protocols` +

# 3. Architecture invariants & verification

## Architecture invariants Codex must not violate

These are hard constraints from `CLAUDE.md`. Violating one either breaks the Kernel×Protocol design, trips CI, or reintroduces a shipped incident.

| Invariant | Why | Enforced where |
|---|---|---|
| **Kernel × Protocol orthogonality** | Adding a kernel (`wgturn`, `xray`) or protocol (`hysteria2`, `wireguard`) must not force edits to `core` / `ssh` / `crypto` / `inventory` / `cli`. Keeps the two trait layers independent so new wire formats are one file + one `register_*` line. | `crates/core` traits + `Registry::validate_server`; `Kernel::supported_protocols()`. A diff that touches unrelated crates to add a protocol is the smell. |
| **No `unwrap()` / `expect()` / `panic!()` / `todo!()` outside `#[cfg(test)]`** | These abort the daemon in production; a subscription fetch must never panic a shared process. | `[workspace.lints.clippy]` in root `Cargo.toml`: `unwrap_used`/`expect_used`/`panic`/`dbg_macro = "deny"`. Fails `clippy -D warnings`. Tests may `#[allow(...)]` locally. |
| **No `unsafe`** | Zero justification in this workspace; forbid removes an entire audit surface. | `[workspace.lints.rust] unsafe_code = "forbid"` in root `Cargo.toml`. |
| **Every inventory write is audited** | Single-operator forensics — every mutation leaves an `audit_log` row so abuse/incident timelines reconstruct. Audit-on-*actual*-mutation (no-op writes must not spam rows — NM-10 contract). | `crates/inventory/src/sqlite.rs` write methods; each transaction-wraps mutation + audit row. Spec tests pin the count. |
| **`real_client_ip_predicate` is the single authority for "real client IP"** | One place decides which `sub_access_log` IPs are genuine external clients vs. our own nodes / LAN canaries; distinct-IP/country/ASN aggregates all route through it so tiles and verdicts can't disagree (TT-3). Safe to `format!`-interpolate — hardcoded ranges, no user input. | `crates/inventory/src/sqlite.rs:577` (`fn real_client_ip_predicate`); consumers at `sub_access_aggregates_for_user`. |
| **CSP `script-src 'self'` — no inline JS in HTML** | The admin UI ships a strict CSP; inline `<script>` / `onclick=` is silently blocked in-browser. Client JS lives in the external `daemon/assets/admin.js` (generic `[data-sse-url]` hooks). | CSP header in the daemon; latent breakage caught when inline SSE logs didn't run (UX-2 note). |
| **maud auto-escapes; never bypass it** | maud escapes interpolated values by default — using `PreEscaped` on user/inventory data is an XSS hole. Injection-safe query params go through explicit encoders (`NINITUX_QUOTE`, `js_single_quote_escape`), not raw string concat. | maud templates in `daemon/src/handlers/admin.rs`; `js_single_quote_escape` helper + smoke test asserting zero bare apostrophes in `confirm()` bodies. |
| **Operator-action policy — admin HTML/errors give NO imperative shell instructions** | Pavel: the operator never opens a terminal. `ssh …`, `systemctl …`, `echo … >> authorized_keys`, `journalctl …` in 4xx/5xx bodies or admin copy is a UX bug. When the daemon truly can't self-fix (banned, no relay), copy says "daemon can't help, use the hoster's serial console / KVM" — it never tells the operator to SSH. | `alert_sink::classify_ssh_failure` + unit test `classify_ssh_failure_recognises_permission_denied` (asserts `!msg.contains(">> ~/.ssh/authorized_keys")`). Shell strings are OK only in `audit_log` payloads + dev doc-comments. |
| **EN/RU parity on every translated string** | Bilingual admin UI; a missing arm is a compile error by design for `K`-keyed strings, a silent English leak for inline pairs. | `daemon/src/i18n.rs`: `t(loc, k)` is an exhaustive match over `K` (adding a key without both arms won't compile); `tr(loc, en, ru)` for one-off body copy. Smoke tests `i18n_ru_renders_translated_body_copy_on_each_page` / `i18n_en_default_renders_english_body_copy` guard tr-arm swaps. |
